\chapter{Release 7 : Qualité, conteneurisation et intégration continue}
\section*{Introduction}
Les releases précédentes ont livré les fonctionnalités de Sellio. Cette dernière release s'attache à la manière de les livrer : une plateforme de six microservices, deux applications React et des modèles Python ne peut pas être vérifiée à la main à chaque modification. Le Sprint 12 met en place des tests automatisés sur les trois technologies du projet, conteneurise l'ensemble de la plateforme avec Docker et automatise sa construction, ses tests et la publication de ses images avec GitHub Actions.

Le code de Sellio étant hébergé sur GitHub, \textbf{GitHub Actions}~\cite{githubactions} s'impose : aucun serveur à maintenir et des machines Linux fournies. Le registre d'images existe, mais il n'est pas utilisé : le pipeline ne déploie pas. \textbf{Docker}~\cite{docker} est retenu pour la conteneurisation : chaque service embarque son environnement d'exécution (Java 17, ou Java 17 et Python 3.12 pour l'analyse), ce qui supprime les différences entre le poste de développement, la machine d'intégration continue et le serveur.

Le \texttt{Dockerfile} des services est \textbf{multi-étapes} : la première étape contient Maven et le JDK, la seconde uniquement l'environnement d'exécution et le JAR, ce qui réduit la taille des images et leur surface d'attaque. Un seul fichier sert les six services grâce à un argument de construction (\texttt{SERVICE}) et à deux cibles (\texttt{service}, \texttt{analytics}).

\subsection{Composition de la plateforme}
Le fichier \texttt{docker-compose.yml} décrit la plateforme de la figure~\ref{fig:archi_physique} : cinq conteneurs PostgreSQL, un par microservice, chacun avec son volume, son contrôle de santé et son mot de passe, les cinq services Java et la passerelle, qui n'attendent que leur propre base, et les deux front-ends. Les secrets (clé JWT, Stripe, Brevo, Decart) ne sont jamais dans les images : ils sont lus au démarrage depuis le fichier \texttt{.env}, exclu du dépôt, dont un modèle documenté (\texttt{.env.example}) est versionné. Dans les conteneurs, la passerelle joint les services par leur nom (\texttt{http://auth-service:8081}\dots) grâce aux variables \texttt{*\_SERVICE\_URL}, alors qu'elle utilise \texttt{localhost} lorsqu'ils sont lancés depuis l'IDE : le même code fonctionne dans les deux cas.

Les trois familles de tests s'exécutent en parallèle sur des machines Ubuntu 24.04 fournies par GitHub, avec mise en cache des dépendances Maven, npm et pip. Les images Docker ne sont construites que si les trois réussissent. Elles ne sont ni publiées sur un registre ni déployées sur un serveur : mettre la plateforme en ligne reste une commande \texttt{docker compose} lancée à la main. Le tableau~\ref{tab:jobs} décrit les tâches. Les durées varient avec le cache : une exécution ancienne, avant les 230 tests, tenait en un peu plus d'une minute, ce qui ne décrit plus la suite actuelle. \section*{Conclusion}
Cette release a rendu la vérification de Sellio reproductible : chaque modification est compilée et testée sur les trois technologies du projet, les images Docker ne sont construites qu'ensuite, et la plateforme se lance en une commande. Le déploiement continu n'est pas en place. Les 230 tests portent sur les règles dont la violation aurait les conséquences les plus graves, en particulier l'isolation des données entre boutiques, puis sur les services, les contrôleurs et les écrans ajoutés pour la CI.
